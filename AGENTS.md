## Quick rules

- `ActivityRecord[]` is the source of truth for runs; maps/charts are derived.
- XP/level and competitive rank are **separate** (see milestone 03). XP awards are **server-authoritative** via `award_run_xp` RPC; local AsyncStorage cache for offline UX.
- **Milestone 02:** Phase A–D shipped; **Phase E hardening** is next.
- **Milestone 05:** Phase 1–6 shipped (feed engagement, Elo UI, friends feed, solo matchmaking, live scoreboard + chat, completion drawer, friend challenges, forfeit, tab indicators, in-app challenge notification drawer). Completed 1v1 solo matches now also post to the feed (`SoloMatchFeedCard`, styled to match `TeamMatchFeedCard`) the same way completed team matches already did — server-inserted `feed_posts` row at `finalize_solo_match` time. See [supabase/SCHEMA.md](supabase/SCHEMA.md).
- **Milestone 06:** Phase 1–4 shipped (account settings, achievements, rank avatar borders, level gates); Phase 5 paywall next. Level gates: `feature_gates` catalog in DB, server triggers + `useFeatureGate` locked UI — never hardcode thresholds in TS.
- **Milestone 08 (shipped v1):** run detail screen — tap any feed run → hero route map (tap → fullscreen `interactive` map modal), primary stats, pace/elevation/HR charts, mile splits (`computeMileSplits` → `summary_json.splits`, null-safe), match badge, likes/comments, and delete own run (`delete_activity` RPC). `RunDetailScreen` + `activityDetailService`. See [milestones/08-run-detail.md](milestones/08-run-detail.md).
- **Milestone 09 (Phase 1-3 shipped):** wearable ingest via **HealthKit** — one integration covers Apple Watch **and** Garmin, no Garmin partner approval. Verified firsthand on-device: Garmin writes workouts + HR to HealthKit but **not** GPS routes, so route is a *quality* signal (unlocks Pace Distribution / Climbing Analysis), **not** an XP/match eligibility gate. `healthKitService.ts`/`healthKitMappers.ts` build real `ActivityRecord[]` from HealthKit workouts (route path for Apple Watch, route-less time-grid path for Garmin); `healthKitVerification.ts` computes the Verified/Unverified tier — deliberately **permissive** (`wasUserEntered=false` + HR series present + plausible pace/HR + within 7-day recency); `HKSource`/`HKDevice`/sample-density recorded in `import_metadata` but not gated, tighten later from real abuse patterns. `healthKitDedup.ts` catches the same run cross-posted into Health by multiple apps (Garmin + Strava both writing separate `HKWorkout`s) via close start-time + close distance. `healthKitSyncService.ts` orchestrates fetch → map → verify → dedup → **auto-publish** (id = `HKWorkout.uuid` for idempotent re-sync; XP/match-crediting gated server-side, see below; **also creates the matching `feed_posts` row** via `createFeedPost` — native runs need an explicit "Add to feed" tap to get one, so this was a real gap the first time through, found because synced imports weren't showing up in the feed) — triggered by a real "Sync Apple Watch & Garmin runs" row in Settings. `ActivityRecord.latitude/longitude` are nullable (done). **Known gotchas**: `queryQuantitySamples`'s `filter: { workout }` silently returns zero results even when real samples exist in that workout's window — confirmed via an unfiltered control query; use `filter: { date: { startDate, endDate } }` against the workout's own dates instead. Also, HealthKit UUIDs come back uppercase but Postgres `uuid` columns return lowercase — the "already imported" id check in `healthKitSyncService.ts` must lowercase both sides, or every re-sync misreports already-imported workouts as cross-app duplicates instead. **Deliberately auto-publish, not review-first** (a user decision) — the pipeline stops right before the upsert with a docblock marking that as the seam for a future review-before-publish flow, so switching later is additive, not a rewrite. **Not yet wired**: Phase 4 background sync (manual trigger only, for now). `syncHealthKitWorkouts` now also skips obviously-junk `HKWorkout`s (a Watch workout started/stopped within seconds while testing) below `MIN_SYNCABLE_DISTANCE_METERS`/`MIN_SYNCABLE_DURATION_SECONDS` (100m / 60s) — counted as `skippedTooShortCount`, surfaced in the Settings sync status line. Also fixed: `buildPostRunSummary` (shared by native and HealthKit-synced runs) previously hardcoded `avgHeartRate: 0` and an empty HR chart unconditionally — real per-point `heartRateBpm` from `records` (present for HealthKit imports, per `import_metadata.heartRateRecordCount`) never reached `summary_json`, so the run detail screen legitimately had nothing to show even when HR samples existed at sync time; now computed via `averageHeartRateBpm`/`buildHeartRateChartFromRecords`. Three more real bugs fixed from on-device testing: (1) `createFeedPost` had no way to backdate `feed_posts.created_at`, so a synced run always showed as "just posted" regardless of when it actually happened — `syncHealthKitWorkouts` now passes the run's own `endedAt` as `createdAt`. (2) Added a hard `MAX_IMPORT_AGE_HOURS` (24h) cutoff — a run finished more than a day ago is treated as a forgotten/backfill sync and skipped entirely (`skippedTooOldCount`), not imported. (3) `matchId` on a synced activity was previously whatever match was active *at sync time*, not necessarily the match that was active *while the run happened* — a run synced late (after its real match ended and a new one started) could get wrongly credited to the new match, silently changing its outcome after the fact; `creditableSoloMatchIdForRun()` now only credits a match if the run's end time actually falls within that match's own `[created_at, ends_at]` window. Note: this window check is client-side only — `credit_match_activity` (server) still checks `match.status = 'active'` (blocks crediting an already-finalized match) but does not independently re-derive whether the activity's timestamp falls inside the match window, so it trusts whatever `match_id` the client wrote; worth hardening server-side later if this needs to be un-spoofable. **Synced runs now award XP with the full post-run drawer UX** (level-up animation, achievement unlocks) instead of silently crediting XP server-side with no client feedback — `syncHealthKitWorkouts` deliberately stopped calling `award_run_xp` itself (it's not safe to call twice for "show the drawer" purposes: a second call reports `xp_earned: 0`/`already_awarded: true`) and instead returns `syncedActivities: StoredActivity[]`; `SettingsScreen.handleSyncHealthKit` awards XP for each one via the normal `presentRunAward(() => awardRunXp(activity))` path — same one `RunScreen` uses for a phone-tracked run. `presentRunAward`'s `showXpGain` already queues internally (`XpGainContext.tsx`), so calling it once per synced activity produces the expected "one drawer closes, next one opens" sequence for a multi-run sync with no new queueing code needed. See [milestones/09-wearable-integration.md](milestones/09-wearable-integration.md).
- **Premium analytics (in progress):** three premium run-detail cards (Pace Distribution → Climbing Analysis → Heart Rate Analysis), all owner-only and ungated (no paywall UI yet — full analysis shown to everyone until that lands), all built on shared `paceSegments.ts` (smoothed, grade-adjusted, moving-time-only pace windows). **Pace Distribution** — personalized Recovery/Easy/Workout/Hard pace ranges computed from the raw per-point track (`activityTrackService`), cached per-user in `user_pace_profiles` (`paceProfileService`, duration-weighted percentiles over ~90 days, not a simple average), classified per-run in `paceDistributionService`. **Climbing Analysis** — terrain distribution, significant-climb detection with gap-bridging, per-climb pacing (thirds/fade/strong-finish), downhill classification, route classification (`climbingAnalysisService`). **Heart Rate Analysis** — `heartRateSamples.ts` cleans raw HR (range/flatline/isolated-spike filtering) before `heartRateAnalysisService` builds personalized zones (from this run's own observed sustained max — no stored user max/resting/threshold HR exists yet, clearly labeled as an estimate), zone distribution, cardiovascular-profile classification, HR drift, pace/HR relationship, and sustained high-HR segments. **Note:** `ActivityRecord.heartRateBpm` is never populated by phone-GPS tracking, so this card still shows "unavailable" for phone-tracked runs — but milestone 09's HealthKit sync now populates real HR for Apple Watch/Garmin-synced activities, so the card activates for those. No cross-run history, matched-climb, or interval-lap analysis for any of the three cards yet.
- **Me tab stats:** `OverallStatsSection` now has range tabs (`OverallStatsRangeTabs` — All Time/Last Week/Last Month/Last Year; `fetchProfileOverallStats(userId, since?)` filters by `started_at`). New `CompetitiveStatsSection` (`competitiveStatsService.fetchCompetitiveStats`) shows overall W-L record (no ties — this system has no tie concept) plus avg distance per match and win rate. Record is read from the **server-authoritative** `player_rank`/`team_rank` `season_wins`/`season_losses` (not derived from `match_participants.points`, which is a binary 0/1 win flag per side, not a real point total, and is left unpopulated for forfeited/unscored matches — summing it misread ties). Always all-time, not range-filtered.
- **Milestone 07 (in progress):** team play — Phase 1–4 shipped: creation/management (`create_team` L10-gated, role-checked RPCs, leader auto-succession), `team_rank` + real Team tab stats (`get_team_overview` / `list_top_teams`), team matchmaking queue (`enqueue_team_matchmaking`, leader/co-leader only; `TeamMatchTab` de-mocked), and real top-N scoring + finalize (`finalize_team_match` sums top-5 point-earners' synced activities per side, applies team Elo via `apply_team_elo_match_result_system`, persists per-team completion; `TeamMatchCompletionProvider`/`TeamMatchResultDrawer` mirror the solo win/loss/tie notification). **Invites & join requests** shipped (`team_membership_requests`; feed-bell notification center + in-app popups + bell/feed-tab badges). Next: Phase 5 — retire the seeded demo match, team season record card. See [milestones/07-team-play.md](milestones/07-team-play.md).
- Summaries in Postgres, bulky tracks in Storage.
- Feed + team screens read from Supabase (`feedService`, `teamService`); feed cards show static route maps from `activities.polyline`; likes/comments persisted on `feed_posts`.
- Post-run “Add to feed” uses `publishActivityToFeed` (sync activity, then `feed_posts` insert).
- XP awards on “Lock in your run” via `award_run_xp` RPC (server recompute); local cache in AsyncStorage; run `npm test` after XP formula changes.
- **Reference catalogs** (`rank_tiers`, etc.) live in **Postgres + seed.sql** — not duplicated TS lists.
- **User state** = numbers (`competitive_rating`, `total_xp`) — not rank title strings on profiles.
- **Schema changes:** migration → `supabase gen types` → commit `database.ts` with SQL → **update all READMEs** (see skill).
- Custom navigation in `src/navigation/` — not file-based Expo Router.
